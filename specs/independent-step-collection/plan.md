### 当前设备准备与优先顺序

1. **T1 实际运行与环境。** 核对 SDK adb、设备列表和 5037 端口归属；如华为手机助手的 hwtransport 占用或替换传输，定位对应进程并恢复 SDK adb 连接，随后复查安装/启动/日志稳定性。安装准备版，展示现有登记或准备页面；补模拟器配置，验证本地保存和重开。
2. **T1 BLE 稳定性。** 复查服务发现、通知/描述符订阅、MTU、读写命令排队、回调及超时/重试的顺序。围绕“连续控制命令发送失败，重连后恢复”的实际现象补日志和可重复用例；错误根因未确认前保留未知。修复后用自动化回归和真实重连重复验证，分别报告证据。
3. **一次性旧记录处置。** 用户确认指定戒指约 5 MB 为上次实验记录，无需保留；不新增恢复、分析或迁移工作。先核对设备与记录身份、当前采集状态、固件 START 的记录边界和覆盖机制，再按已确认范围处理。处置记录只保留设备代号、前后状态与所用命令，避免影响其他设备、文件或实验数据。新实验尚未安全保存的记录继续受待传保护，不能沿用这次旧记录例外。
4. **T2 分步接通。** 先做 session 身份/状态与开始停止证据，再接整段参考数字可靠保存，然后接下载/打包与恢复，最后接上传和 T3 读取；每个小切片分别记录软件与设备证据。Q01/Q02 只在影响对应交互实施时集中询问；Q03 按已确认的缺失原因保存分支实施。普通工程选择自主推进。

## 3. T1 之后的数据与状态实现顺序

### T2a：采集请求账本底座

本小步解决“采集请求发出后，重开还能找到同一个 session 及其身份”的软件前置问题，涉及 `FreeLivingSessionStore`、对应 JVM/Android 测试和 Gson 严格解析依赖。它尚未接入界面或 BLE，因此当前 APK 的可操作范围仍为 T1 准备页。

1. 在已有、稳定的应用私有目录保存唯一 session，冻结编号、installation ID、佩戴位置及戒指。先持久化请求，再由后续控制器发送命令。
2. 分开记录开始请求、开始确认、停止请求和停止确认；缺设备边界证据时真实起止为 null。重复请求保留原 ID/首次时间，错误戒指或设备 session 回复不能推进状态。
3. 文件同步、原子替换后再同步目录；失败不返回成功，损坏文件保留。恢复及幂等重试再次检查持久性，停止后未安全落盘的记录继续阻挡新 session。
4. 以身份串联、重复操作、跨实例恢复、写入/目录同步失败、JSON 损坏、手机回拨及跨午夜测试验收；Android 测试另检查默认文件实现可运行。具体执行结果见 validation 第 8 节。

此步暂不提供开始按钮、BLE START/STOP、后续边界补证、步数确认、下载或待传锁释放。下一步控制器必须验证新设备记录确属本次请求；一次 STATUS 回复仅表达当前状态，不能独自证明新采集已经建立。后续从 LIST/原始样本补边界需独立保存来源，不能靠重复确认改写首次事实。真实断电及完整恢复按 B08 留待设备验证。

### 后续接通顺序

1. **先定义契约和版本分路。** 按 requirements 第 4 节同步 Android、本地 JSON、manifest 和 Python 校验，补 valid/missing/unreliable、free_living/unlabelled、边界证据和异常。暂定保留容器 v2 与 rfbin v2，新增 step_schema_version=1 和 daily_activity_v2；新后端先兼容或联合发布，避免旧白名单拒收新包。
2. **冻结采集身份，保存时间证据。** 保留唯一 session，分开手机请求/确认、设备记录和有效边界。修改停止确认与下载完成路径，避免当前时间回填采集起止；原始时间锚/包可追溯，时间修正另记。采集重启、设备 reboot、手机改时和边界丢失有明确状态。停止边界无法恢复时先保全当前读数及异常，保持 Flash 保护，恢复后确认可安全读取再下载。
3. **参考数字与异常先可靠保存。** 在下载前保存数字、来源、填写时间与质量状态；失败不推进任务。先实现正常值和零值，再实现 Q03 定稿的缺失分支。最终确认前可修改；确认后参考快照锁定按 Q02，文件清单、下载完成时间和完整性证据随后补齐，首次发送前冻结完整 ZIP。测试旧缓存失效及上传竞态，避免参考锁定阻断处理字段持久化。
4. **保持多文件和失败恢复。** 复用串行 BLE、Flash 断点、CRC/SHA 与上传队列。恢复沿用原 session；区分已落手机与仍只在戒指的文件，前者不因云端断网长期阻止新采集。保留低电/容量/空间失败的已知数据，不把下载成功等同于采集完整。
5. **后端按 session 组织评估输入。** 保留 raw_files 与派生 CSV 的一对多映射，关联唯一参考总数；IMU 去重后汇总，PPG 单独处理。自由活动 CSV 活动真值留空，下游过滤未标注。历史类别和将来算法来源明确分路。
6. **再做质量和每日结果。** 同包/同批去重、同 ID 异包冲突、不同 ID 重叠检查；边界/缺口/异常影响分析资格。按记录时区汇总有效 session，展示覆盖时段和跨日未分配项。完整目标日结论等待明确的目标时段与覆盖证据。

## 4. 源码影响与复用边界

完整行号与差异见 [change-review.md](change-review.md)。最关键的调整是：

- T1 的独立启动界面、`PreparationStore / RingPreparationController` 提供登记、记忆和只读设备准备；六位置与 BLE 协议沿用。旧登录及采集组件保留在受控基线，独立导航不调用其运行流程。
- T2 的 `CapturePurpose / RingCaptureService`：将真实采集从必选单活动转为自由活动，接通开始/停止确认/填数交互及 session 快照；原始通信协议继续复用。
- `RingCaptureService / HealthFlashDownload / HealthRawV2`：修正 ended_at_ms 的语义；对时间归一化保留原始依据和修正标记，区分实际缺失和连接缺失。
- `UploadSessionStore / UploadWorker`：新增参考与质量字段、schema、多文件映射和冻结规则。已有 JSON 临时写入、任务恢复及重试是复用起点，新增字段的崩溃可靠性仍须验证。
- `DailySummaryStore`：原统计基于 BLE 连接区间，不能直接充当真实信号覆盖率或参考步数日累计。
- 后端 `app.py / label_daily_activity.py / health_raw_v2.py / sync_all_and_label.py`：同步更新白名单、显式版本/参考校验、未标注路径、时间审计、独立活动同步及 session 级结果。现有归档目录按历史保留，后端修改发生在后续建立的工作副本。

## 5. 长时验证安排

B16 是设备验证工作，具体时长为试验梯度而非软件限制。暂定从约 10 分钟开始，经约 1 小时、数小时，再根据电量和容量证据探索接近一天；每级先完成下载、解码和样本覆盖核查，再安排下一等级。产品可用范围按成功实测工况描述，失败等级及尚未达到的目标保留。

每级记录手机/戒指/固件/采样设置、起末电量、Flash 记录量、各原始文件大小、手机下载/ZIP 峰值空间、开始/停止/填写/下载各时刻、有效样本覆盖、下载/上传/解码耗时及故障结果。容量查询不受支持时说明限制，以可验证的记录量给出下限，不声称测得容量上限。专用测试数据用于满存储/掉电/空间不足场景；原始实验数据先保全。

原代码中的 48 小时时间窗口、上传读取超时和后端解压限额是程序边界。它们分别检查兼容性，不作为“能连续采集多久”的设备结论。长时通过需要真实包和源数据审计，静态源码与构建成功只提供前置证据。

## 6. 文档审阅、验证与提交

每个切片先核对用户流程、边界、S/T/B 对应与 Q01–Q03 状态，再实现对应功能。持久化和设备状态改动安排独立只读审查，意见包含位置、触发条件、影响与依据；主代理核实修复后重跑受影响的测试、构建与实际流程。设备条件不足时明确标注待执行，不用自动测试代替实物结论。

每个实现切片记录源码提交或文件指纹、配置代号、APK 哈希、工具/设备版本、命令/步骤与结果；真实链接、token、设备标识和研究数据保存在受控本地环境。日志/截图使用忽略的本地证据目录，提交只保留脱敏结果和证据路径；分享前检查截图中的私人信息。按用户已有授权，在审阅和适当验证后仅提交相关文件，保留其他窗口改动；更新 validation 与本功能 change-review，汇报提交编号、通过/待执行项、真实页面与下一步。
