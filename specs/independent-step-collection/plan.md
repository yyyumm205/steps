## 3. 数据与状态实现顺序

1. **先定义契约和版本分路。** 按 requirements 第 4 节同步 Android、本地 JSON、manifest 和 Python 校验，补 valid/missing/unreliable、free_living/unlabelled、边界证据和异常。暂定保留容器 v2 与 rfbin v2，新增 step_schema_version=1 和 daily_activity_v2；新后端先兼容或联合发布，避免旧白名单拒收新包。
2. **冻结采集身份，保存时间证据。** 保留唯一 session，分开手机请求/确认、设备记录和有效边界。修改停止确认与下载完成路径，避免当前时间回填采集起止；原始时间锚/包可追溯，时间修正另记。采集重启、设备 reboot、手机改时和边界丢失有明确状态。停止边界无法恢复时先保全当前读数及异常，保持 Flash 保护，恢复后确认可安全读取再下载。
3. **参考数字与异常先可靠保存。** 在下载前保存数字、来源、填写时间与质量状态；失败不推进任务。先实现正常值和零值，再实现 Q03 定稿的缺失分支。最终确认前可修改；确认后参考快照锁定按 Q02，文件清单、下载完成时间和完整性证据随后补齐，首次发送前冻结完整 ZIP。测试旧缓存失效及上传竞态，避免参考锁定阻断处理字段持久化。
4. **保持多文件和失败恢复。** 复用串行 BLE、Flash 断点、CRC/SHA 与上传队列。恢复沿用原 session；区分已落手机与仍只在戒指的文件，前者不因云端断网长期阻止新采集。保留低电/容量/空间失败的已知数据，不把下载成功等同于采集完整。
5. **后端按 session 组织评估输入。** 保留 raw_files 与派生 CSV 的一对多映射，关联唯一参考总数；IMU 去重后汇总，PPG 单独处理。自由活动 CSV 活动真值留空，下游过滤未标注。历史类别和将来算法来源明确分路。
6. **再做质量和每日结果。** 同包/同批去重、同 ID 异包冲突、不同 ID 重叠检查；边界/缺口/异常影响分析资格。按记录时区汇总有效 session，展示覆盖时段和跨日未分配项。完整目标日结论等待明确的目标时段与覆盖证据。

## 4. 源码影响与复用边界

完整行号与差异见 [change-review.md](change-review.md)。最关键的调整是：

- `CapturePurpose / MainActivity / RingCaptureService`：从必选单活动转为自由活动入口，增加清零/停止确认/填数交互；原始通信协议继续复用。
- `RingCaptureService / HealthFlashDownload / HealthRawV2`：修正 ended_at_ms 的语义；对时间归一化保留原始依据和修正标记，区分实际缺失和连接缺失。
- `UploadSessionStore / UploadWorker`：新增参考与质量字段、schema、多文件映射和冻结规则。已有 JSON 临时写入、任务恢复及重试是复用起点，新增字段的崩溃可靠性仍须验证。
- `DailySummaryStore`：原统计基于 BLE 连接区间，不能直接充当真实信号覆盖率或参考步数日累计。
- 后端 `app.py / label_daily_activity.py / health_raw_v2.py / sync_all_and_label.py`：同步更新白名单、显式版本/参考校验、未标注路径、时间审计、独立活动同步及 session 级结果。现有归档目录按历史保留，后端修改发生在后续建立的工作副本。

## 5. 长时验证安排

B16 是设备验证工作，具体时长为试验梯度而非软件限制。暂定从约 10 分钟开始，经约 1 小时、数小时，再根据电量和容量证据探索接近一天；每级先完成下载、解码和样本覆盖核查，再安排下一等级。产品可用范围按成功实测工况描述，失败等级及尚未达到的目标保留。

每级记录手机/戒指/固件/采样设置、起末电量、Flash 记录量、各原始文件大小、手机下载/ZIP 峰值空间、开始/停止/填写/下载各时刻、有效样本覆盖、下载/上传/解码耗时及故障结果。容量查询不受支持时说明限制，以可验证的记录量给出下限，不声称测得容量上限。专用测试数据用于满存储/掉电/空间不足场景；原始实验数据先保全。

原代码中的 48 小时时间窗口、上传读取超时和后端解压限额是程序边界。它们分别检查兼容性，不作为“能连续采集多久”的设备结论。长时通过需要真实包和源数据审计，静态源码与构建成功只提供前置证据。
