## 2. 实际用户流程

这里的执行者是项目开发者或协助测试的同伴；正式被试招募、日常采集频次和实验方案在后续阶段确定。

1. 配置原版用户服务，以可用测试用户名登录。原版规则为 3–24 位字母或数字，用户名经服务解析得到 `participant_id`。
2. 授予所需手机权限，搜索并连接指定 Ringo 戒指。记录手机系统、戒指标识、电量与固件查询结果。
3. 进入“日常活动采集”，选择走路及实际佩戴位置；暂定关闭 Polar。原版仍显示其他活动和睡眠入口。
4. 点击“开始采集”，等待显示“采集中”后走路；结束活动并站定，再点击“结束采集 → 结束并立即上传”。
5. 原版显示活动评价页。暂定评分和文字均留空，点击“保存评价并继续”。这一步仍是原版流程的一部分。
6. 等待戒指停止、Flash 收尾、下载和本地保存；核对同一个 session 的状态与文件，再核对上传结果。
7. 本机 Python 从对应云盘测试目录同步 ZIP，校验、导入并生成加速度 CSV；用同一个 session 的记录核对完整链路。

“固件”是运行在戒指内部、控制传感器和蓝牙的程序。交接包未提供这枚实物戒指的版本记录；协议测试里的 `1.2.3.4` 是样例。App 支持查询版本，实际值待连接读取；若不支持查询，记录提示并请同伴补充。

## 4. 数据含义与时间边界

- 一个 session 对应一次开始至结束的活动，沿用手机生成的 UUID。`.rfbin` 头内的戒指 HEALTH session ID 是另一个协议编号，需要记录两者关联。
- `participant_name` 是测试用户名，`participant_id` 来自原用户服务。云盘文件夹名不决定被试归属。
- 原始包 v2 保存 Flash payload；公开 manifest 保存活动、佩戴位置、文件大小和 SHA-256。50 Hz 指每秒约 50 个加速度采样点。
- 当前源码中未找到 `ground_truth_steps`、`ground_truth_source`、`ground_truth_recorded_at_ms` 的实现。本阶段不要求 App 收集参考步数。
- 后续新增的参考步数应覆盖同一段戒指采集时间，例如“开始后走的一段路，共 300 步”；全天累计读数需要先转换为这一段的步数。计步器清零或读数相减的具体实验操作留待步数功能规格确认。
- 时间审阅发现：`RingCaptureService.completeHealthDownload()` 使用下载完成时刻写入原始文件结束时间；`finalizeUploadGroup()` 使用整理时刻写入 session 结束时间。开始字段也早于戒指确认开始采集。因此这些字段与真实运动边界的差值需要实测。
- 本阶段记录点击开始、确认采集中、停止活动、发送停止、戒指停止确认、下载完成、manifest 起止时间和 CSV 首末时间。对差值给出毫秒或秒数及原因，保留原始值。后续步数评估前需明确有效区间和对齐方法；本次基线通过仅表示数据链路可用。

## 5. 异常与恢复规则

| 情形 | 验证时的处理与判据 |
| --- | --- |
| 首次登录提示“尚未配置用户服务” | 记录为前置条件未满足；补齐原服务配置后继续，不把登录成功预填进记录 |
| 无法读取固件版本 | 记录完整提示及戒指标识，向同伴核实；其他连接检查可继续，固件信息项保持待确认 |
| 戒指断连 | 用原戒指、原用户重连；断连时停止操作可能被拒绝，必须以实际停止确认确定状态 |
| Flash 下载中断 | 记录已持久化的下载量和 session；重连后从有效断点恢复，允许安全重读部分字节，完成后校验完整文件。待传锁期间应阻止新采集覆盖记录 |
| App 重启 | 本轮最小检查在已保存到手机、等待上传的阶段，通过测试手机“强行停止”结束 App 进程，再手动打开。保留应用数据，核对 session、活动、佩戴位置和文件哈希；采集中强制停止、手机重启等更广恢复矩阵列入后续 |
| 网络不可用或上传中断 | 记录 `queued`（排队）、`uploading`（上传中）或 `failed`（失败）；保留本地原始文件和同一 session，恢复网络后跟踪原任务；失败记录通过“本地待上传”重试 |
| 未出现“本地待上传” | 先核对真实状态。源码只在该列表显示 `failed`，排队中的任务不必出现在其中；离线排队也不等于已经触发上传失败 |
| 更换云盘地址 | 在新 session 开始前配置并重新构建；旧活动 session 保留原 `upload_link`，源码的地址迁移只处理睡眠记录。旧记录的迁移另行制定方案 |
| 重复导入 | 相同 `session_id`、相同 ZIP 哈希应跳过；相同 ID、不同内容应报告冲突，保留原文件和账本 |
| 文件损坏、保存失败或任务丢失 | 记为失败并保留日志和现有文件；在审阅问题后安排修复，不用“删除数据/放弃任务”代替成功恢复 |

## 6. 已确认、暂定与待确认

### 已确认

- 用户有 Android 11 及以上测试手机。
- 测试戒指和充电盒可用。
- 使用用户自己的清华云盘测试文件夹，Python 后端先在本机运行。
- 本轮只进行规格准备与审阅，业务实现仍在规格审阅之后安排。用户已授权按独立小步骤完成审阅和适当验证后自行本地提交；具体规则见 plan.md 第 1 节。

### 暂定方案

| 编号 | 默认值 | 理由与影响 |
| --- | --- | --- |
| A01 | 主流程选择走路约 3 分钟，结束后站定操作手机 | 足够产生一小段运动信号；适合先核对链路，时长不是正式实验要求 |
| A02 | 不勾选 Polar；原版评价评分、文字留空 | 减少外部设备与输入条件，同时走完原版结束流程；HEALTH 实际输出可能仍含 PPG |
| A03 | 一个测试用户、一枚戒指、一个独立测试目录 | 便于逐项核对归属，减少与其他数据混合 |
| A04 | Python 先定向同步活动目录，再用现有导入器处理 | 原一键脚本还依赖 Junction/Oura；可复用已有下载函数和导入器完成活动链路，详见 plan.md |

### 待确认或待补录

| 编号 | 内容 | 为什么需要；建议或选项 |
| --- | --- | --- |
| Q01 | 手机品牌、型号、具体 Android 版本 | 后续复现需对应设备；测试时从“设置 → 关于手机”补录即可 |
| Q02 | 实物戒指固件版本 | 不同固件可能有协议差异；建议连接后读取，查询不支持时向同伴核实 |
| Q03 | 测试云盘文件夹的实际位置与读取权限 | 需匹配手机上传链接、资料库 ID、目录、Python 凭据；建议后续一起配置并以同一文件核验，不在规格中保存秘密值 |
| Q04 | 能否取得原用户服务地址、注册码和可用测试用户名 | 当前本机只有 SDK 路径配置，首次登录受限制；建议向同伴复用测试服务。若拿不到，继续桌面检查，真机采集保持受条件限制；另建或替换登录方式需另行规格 |

后续步数功能还需要决定计步器操作和有效时间区间。依据是第 4 节已确认的时间语义差异。建议正式采集前站定准备、戒指确认开始后再活动、结束活动后站定停止；本轮仅保留这个建议，不把它定为已批准的实验流程。
